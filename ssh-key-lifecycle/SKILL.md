# SSH key lifecycle

## When to Use
Use for standardized per-client/app/host public-key inventory, choosing an SSH authentication method, registering vault-backed keys, validated host config, OpenSSH connectivity checks, or tailnet provisioning plans. Bitwarden is the supported default; KeePassXC is supported through its SSH-agent integration, and macOS Keychain is an explicit local-file option. The broader M1–M12 matrix in `references/auth-methods.md` compares manual, Mac-only, and alternative methods without claiming they are implemented. Read `references/security-and-setup.md` when choosing a backend. Scripts operate out-of-process and return only public information.

## Remote client control plane
Hermes may run on a server while the user speaks from a Mac through Wave Terminal or SSH. Before asking the user to run local checks or suggesting A2A, determine where this terminal actually runs, then look for an existing authorized path **back to the Mac**. A Wave remote `wsh` may expose local-file bridging (`/~/`), but do not assume it can execute local commands. Inspect SSH Host aliases, the pinned host key and the authorized *public* fingerprint without reading private key bytes or dumping any server login-key file; verify the Unix login name instead of assuming the stored `User` is current. Test only a noninteractive, public-key, strict-host-key, no-agent-forwarding, no-control-master, read-only SSH command. Once authenticated, execute Mac-specific probes through that channel; a skill script running on the server is **not** running on the Mac. A2A is for independent agents, not a prerequisite to run OS commands over an existing SSH channel.

For a cross-tailnet target, inspect Tailscale's active account and peer identity **on the Mac**, not on Hermes's server. Validate an exact supplied IP before lookup and do not connect to it until its peer identity is known: a shared device may have a remapped address. Do not switch the Mac's active tailnet profile if the current SSH/Wave control session depends on that profile unless a separate recovery route is tested. A membership invite, a second saved profile, and a shared-in device are different states; if the target is not visible, ask the owning admin about a device share or a safe alternate path instead of pretending the current tailnet can reach it. A socket file alone does not prove a vault SSH agent is running or that a biometric prompt will fire for every signature.

## Quick Reference
From this skill directory:
- `scripts/auth-method-select.sh --multi-machine yes|no --human-per-use yes|no --existing-key yes|no --reduce-prompts yes|no --tailnet-ssh yes|no|unknown [--platform linux|darwin] [--choose M#]` returns read-only candidate JSON and, only when explicitly chosen, illustrative config lines. The actual method is a human choice; do not treat a recommendation as authorization or an unsupported method as implemented.
- `scripts/key-search.sh --doctor --backend bitwarden|keepassxc|apple-keychain` checks the desktop executable, selected agent socket, and approval UI without changing state. `bw` is an optional CLI; its absence does not mean the desktop app is absent.
- `scripts/key-register.sh <client> <app> <host> --backend <name> --auth-method M2|M4|M9 --public-file /absolute/path.pub --vault-ref <nonsecret-item-id>` records an **already generated** Ed25519 public key (legacy alias: `keygen.sh`; method auto-derives for older callers). The file must be `~/.ssh/id_ed25519_<client>_<app>_<host>.pub` and mode 0600. M2 maps to KeePassXC, M4 to Apple Keychain, M9 to Bitwarden; mismatches fail before approval. No private key is generated by this script.
- `scripts/key-search.sh [substring]` reads fingerprints and metadata only.
- `scripts/config-append.sh <alias> <dns-name> <registered-name>` appends a restricted Host block; `scripts/ssh-check.sh <alias>` makes a real SSH connection, runs remote `true`, discards remote output, and returns status only if OpenSSH reports public-key authentication. Both request separate local approval.
- `scripts/ssh-exec.sh <alias> -- <program> [arguments...]` first verifies public-key authentication, then separately approves the exact remote command and executes it. It returns exit status and command digest only; remote stdout/stderr never enters the transcript. Never pass credentials in remote arguments. Explicitly verify any claimed remote mutation with a second, independently approved operation.
- `scripts/rotate.sh --plan <old> <successor>` and `scripts/ts-bootstrap.sh --plan <target>` are read-only; execution deliberately disabled until remote authorization and rollback are tested.
Registry and audit: `${HERMES_HOME:-~/.hermes}/state/ssh-keys.jsonl` and `ssh-audit.jsonl`. New registry records include `auth_method`, **non-attested** `prompt_cadence`, `exportable`, `mac_bound`, `provider_path`, `agent_socket`, `control_persist` and `min_openssh_server`. Bitwarden items are exportable through the vault's JSON export; do not describe them as nonexportable. Existing rows without method metadata remain readable; do not infer that vendor per-request approval is enabled from a registry entry. Journal is append-only by application convention, not tamper-proof.

## Choose authentication before registration
1. Read `references/auth-methods.md` and ask the five explicit questions: multi-machine use, human presence for each *fresh* authentication, existing key retention, prompt frequency, and whether the target uses Tailscale SSH rather than plain OpenSSH over the tailnet. Feed answers to `auth-method-select.sh`; answer unknown rather than guessing target interception. Network ACLs/grants apply to either transport. Tailscale SSH check mode is a separate `ssh` policy action, not a network ACL action; key-based auth is bypassed on the intercepted path.
2. Present candidate methods with their **implementation status**. Select only after the human resolves any tradeoffs. M1 is manual encrypted-disk baseline; M2/M4/M9 are the only registration backends. M3 is a manual agent modifier, M5/M6 are macOS CTK proposals needing Tahoe/provider/server tests, M7 (Secretive) needs external-app review, M8 (fssh) is research-only, M10 multiplexing is disabled in skill-managed SSH, and M11 is an operation gate rather than authentication. M12 is an alternative transport, not a key backend. Do not create or import keys, change PAM, configure CTK/Secretive/fssh, or change tailnet policy from this planning step.
3. Preserve per-use consent: `UseKeychain` is not Touch ID per connection, while Bitwarden's approval cadence depends on desktop settings and must be tested twice. An existing key can be kept as M1/M2/M4 or imported to Bitwarden by the human; M8 is not the only possible migration. Never put private keys or passphrases in CLI args, tool results, or vault exports handled by Hermes. If M10 is requested, explain that connection reuse collapses fresh-auth/signing prompts and is incompatible with this skill's default un-multiplexed verification; do not silently enable it.

## Procedures
1. Bitwarden: in the desktop/web UI generate an Ed25519 SSH Key item; on the desktop enable SSH Agent and set authorization to ask on each request (verify twice; do not assume default). Export only the public key to the expected `.pub` file, set `SSH_AUTH_SOCK` to Bitwarden's documented socket, and verify `ssh-add -L` offers its fingerprint. On Linux, native, Snap, and Flatpak desktops have different documented socket paths: consult `--doctor` and the setup reference. A running app alone does not mean the user is signed in or the agent is enabled. `bw get item` may expose the PRIVATE field: never use it for discovery, registration, or output.
2. KeePassXC: import an existing Ed25519 key into a KeePassXC entry *using its GUI*, enable its SSH Agent integration, and load the entry into a running OpenSSH agent (optionally require confirmation on signing). KeePassXC is an **agent client**, not a vault-backed signing agent; the key is loaded into the external ssh-agent. Only run the script after confirming `SSH_AUTH_SOCK` points to that agent and `ssh-add -L` offers the key. Do not automate plaintext generation/import through transcripts. KeePassXC does not provide per-use Touch ID by itself.
3. macOS Keychain: this backend stores the passphrase for a passphrase-encrypted local Ed25519 private key, **not** the private key in Keychain. Register only after loading the key in macOS ssh-agent and exporting its public key to the expected path; registration rejects an unencrypted private file. The separate macOS approval script requires Touch ID via LocalAuthentication with no password fallback for register/config/check. Secure Enclave via Secretive is a different product with EC keys, outside this Ed25519-only v1 backend.
4. Register, then configure an alias with the validated script. For vault agents it binds `IdentityFile` to the public key; for macOS Keychain it binds the encrypted private file and adds `UseKeychain yes` / `AddKeysToAgent yes`. `IdentityAgent` selects the agent; password fallback and connection multiplex reuse are disabled. Check the host's SSH host key out-of-band and add it to known_hosts before running `ssh-check.sh` (which uses `StrictHostKeyChecking=yes`). Vendor sign prompts and this skill's local approval are separate.
5. Over a tailnet use ordinary OpenSSH: Tailscale grants/ACLs govern the network path. The server-side Tailscale SSH setting may intercept tailnet port 22 and bypass OpenSSH key auth; `ssh-check.sh` refuses a connection that did not authenticate with publickey. Use `ssh-exec.sh` for bounded, explicit nonsecret commands only, with host-key verification already complete. Bootstrap and rotation remain plans, not working automated workflows.

## Approval and limits
- macOS mutating scripts run `scripts/biometric-approve.swift` via `swift` and require Touch ID in a separate process. It is not verified live on a Mac yet. Linux runs `zenity` for a human GUI approval, not a biometric. If no GUI/biometric path exists, deny; do not auto-approve or switch to insecure generation. Approval timeout is 600 seconds.
- Vendor signing consent is not a generic approval for config writes. The public metadata in tool results is safe by design for these commands, but a normal terminal capable of arbitrary commands is not a security sandbox. Hard policy against an adversarial agent requires restricting raw terminal/file access or using a separate privileged broker. Ordinary trusted-agent SSH use does not require a new Unix account; don't confuse threat-model hardening with a prerequisite to operate.
- An SSH exec success status alone does not prove the intended remote state. It performs a fresh publickey preflight with connection multiplexing disabled; recheck the result with another command before reporting completion. Never treat its simple credential-argument rejection as comprehensive secret detection.
- Avoid `ssh-keygen -N "$(vault read ...)"`, `ssh-keygen -p -N <passphrase>`, and `tailscale up --auth-key=$TOKEN`: secret argv exposure. Use an interactive human-controlled passphrase-change flow instead. Do not pass Bitwarden CLI session keys into chat. Never print/private-dump vault items. `rm -P` does not reliably erase SSDs.

## Verification Checklist
- [ ] `scripts/key-search.sh --doctor --backend <name>` shows a usable selected socket and approval UI.
- [ ] `auth-method-select.sh` has explicit Q1–Q5 answers, refuses impossible Mac-bound multi-machine choices and returns no secret data or side effects. `--choose` is explicit; the selector cannot prove a vendor prompt, target transport, or Mac feature gate.
- [ ] Registry's new method metadata matches the actual implemented backend. For M9, `exportable=true` and prompt cadence is *vendor-configured*, not attested; M4 is portable key material but macOS-specific integration. Legacy rows remain readable.
- [ ] On Snap Linux, `SSH_AUTH_SOCK` uses the documented per-user Snap socket, not an arbitrary agent; `--doctor` reports the desktop executable independently of the optional `bw` CLI.
- [ ] Fingerprint of the exported public key matches the selected agent; source vault's per-use prompt tested twice.
- [ ] Register/config audit events contain only metadata; no private file generated by this skill.
- [ ] Host block rejects injected directives and wildcard overlaps; `ssh -G -F <temp-config> <alias>` confirms effective options without connecting.
- [ ] `ssh-check.sh` succeeds with publickey, fails with `none` (Tailscale SSH), never emits remote stdout/stderr; no existing multiplexed master reused.
- [ ] `ssh-exec.sh` shows the exact target/command in the GUI approval, logs approval plus outcome/digest, and returns no remote output. Test failure and denial paths, not just success.
- [ ] Mac Touch ID actually prompts under the Hermes/tmux launch context before claiming biometric verification.
- [ ] Tailnet tag/ACL, server-side RunSSH, remote bootstrap-key removal, and negative access tests are required before calling provisioning complete.
- [ ] Static `skills_guard` currently rates SSH-specific code/prose as caution; manual review required, not a passing scan.
